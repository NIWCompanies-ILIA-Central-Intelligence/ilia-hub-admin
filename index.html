One intelligent workspace. Every NIW role. Plain-language help that gets real work done.
Today, how NIW⟷ILIA actually runs — what's done inside ILIA vs. outside it, who owns which process — lives scattered across people's heads, chats, and tools. CIH makes that operational reality explicit, shared, and queryable. The payoff: dramatically faster onboarding, expedited day-to-day workflows, and one NIW-owned system that knows the platform end to end.
The Core Idea — One Pattern, Every Role
CIH doesn't build a different tool for each department
Every role climbs the same four-step ladder of help — they just reach different rungs depending on the job.
01
Know
Knows the role's processes, docs, and source-of-truth — and answers from them.
"How does the DBR workflow route a notice?"
02
Diagnose
Pulls signal across systems — session data, code, records — and explains what's happening.
"Agent John can't log in — what's going on?"
03
Draft
Produces the artifact for review — a ticket, a doc, a prototype, a message.
"Draft a new agent-onboarding training doc."
04
Act
Executes into the live system — and records what it did.
"Send Adam a DBR notice and update ILIA."
Support lives mostly on Diagnose. Operations reaches Act. Marketing works in Draft. Product & Dev build on Act. Same ladder, different reach — which is exactly what makes one platform serve the whole company.
Role-Based Access — Everyone Stays in Their Lane
Each role is granted only the capabilities its job requires — nothing is assumed, and anything not explicitly granted is denied by default. This is what lets us safely give the whole company access to one powerful system.

How access is defined under the hood — the authority grid ›
Each role's authority is a precise grid: which systems it can touch, and to which rung. Example — the Product / PM pilot role:
SystemKnowDiagnoseDraftAct
JIRA / Confluence✅✅✅create / update
GitHub + local sandbox✅✅✅repos / push
ILIA production dataread✅—no production writes
Support, by contrast, has no GitHub access of any kind — "Support doesn't get a developer sandbox" is written as data, not left to guesswork. The same grid is reused at every stage of rollout: first as a rule the system follows, then as the literal configuration of each role's workspace, eventually as the access control in the portal app.
How We Get There — Three Stages
The same access design is enforced progressively harder. Nothing gets rebuilt between stages — it gets promoted.
Stage 1 — Shared Workspace
Available Now
One CIH workspace with all tools connected. Roles defined and self-enforced by the system. Fast and flexible — enough to prove every role.
Stage 2 — Role-Scoped Workspaces
Next
One workspace per role, connected only to the tools that role is allowed to use. Restriction becomes physical, not just a rule — and requires no engineering.
Stage 3 — The CIH Portal
Future Build
A branded, NIW-owned web app. Per-person login, real role enforcement, full audit trail. The daily workspace for every employee — no Claude.ai needed.

Built With Governance & Safety First
Because CIH can eventually act on live systems, it is designed conservatively from day one:
Deny by default — a role can only do what it has been explicitly granted. If CIH is unsure, it stops and asks.
Production is gated — CIH does not read or write live ILIA client data until it clears security & compliance sign-off.
Compliance-sensitive actions are logged — anything touching workflows like Death Benefit Reduction requires a recorded authorization trail and human green-light.
A reversal path comes first — every "act" capability has a clear way to catch and undo a mistake before it ever goes live.
